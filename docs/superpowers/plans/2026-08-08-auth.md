# Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add real login, signup, session handling, and route protection to the Tlabli app, backed by the already-live Supabase project — without changing what `/dashboard` displays (it stays on mock data, per the approved design).

**Architecture:** Switch the browser Supabase client to `@supabase/ssr`'s `createBrowserClient` so sessions are cookie-based; add `middleware.ts` (its own self-contained server client, per the standard `@supabase/ssr` Next.js recipe) to gate `/dashboard` and `/admin`; add a `/login` page and wire onboarding's final step to real `supabase.auth.signUp()` plus a new `create_restaurant_with_owner` Postgres RPC that atomically creates a restaurant and its first owner row, bypassing the circular RLS bootstrap problem in one narrow, controlled place.

**Tech Stack:** Next.js 14 (App Router), `@supabase/ssr` (new), `@supabase/supabase-js` (already installed), PostgreSQL (via Supabase, live project already created).

## Global Constraints

- Email + password only — no magic link, no phone/OTP.
- Platform admin identity is a server-only env var (`PLATFORM_ADMIN_EMAILS`, comma-separated, no `NEXT_PUBLIC_` prefix) — no new table.
- `/dashboard`'s displayed data does NOT change in this plan — it keeps reading `lib/mock-data.ts` via `restaurants[0]` exactly as today, for any logged-in user. Only who can *reach* `/dashboard` changes, not what it shows.
- `SUPABASE_SERVICE_ROLE_KEY` is never read, referenced, or used by any application code or any task's automated verification in this plan — only by `scripts/seed-staff-logins.mjs`, which the user runs themselves, locally, after this plan is implemented.
- SQL (`supabase/sql/05_auth.sql`) cannot be executed by any task in this plan — there is no `psql`/`docker`/Supabase CLI available, and applying new SQL to the live project requires pasting into Supabase Studio, which only the user can do. Verification for that one task is manual read-through, same as every file in the schema/RLS plan.
- Everything else in this plan (browser client, middleware, login page, sidebar logout) CAN be verified live against the real project using the already-present `NEXT_PUBLIC_SUPABASE_ANON_KEY` — e.g. attempting `signInWithPassword` with a wrong password against the real project and confirming a real error comes back. Prefer this over pure code reading wherever the task doesn't depend on `05_auth.sql` being applied yet.
- Follow existing code style: `"use client"` client components with inline handlers (no Server Actions anywhere in this codebase), Tailwind utility classes inline, `@/` path aliases, double-quoted strings, no comments except where a hidden constraint is genuinely non-obvious.

### Task 2: Middleware — route protection for `/dashboard` and `/admin`

**Files:**
- Create: `middleware.ts` (repo root, alongside `package.json`)

**Interfaces:**
- Consumes: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `PLATFORM_ADMIN_EMAILS` from `process.env` directly (NOT via `lib/supabase/client.ts` — `createBrowserClient` expects a real browser `document`, which doesn't exist in Next.js Middleware's Edge runtime, so this file builds its own server-oriented client inline, per the standard `@supabase/ssr` middleware recipe).
- Produces: nothing other tasks import — this is a Next.js convention file, invoked automatically by the framework for every matched request.

- [ ] **Step 1: Create the file**

Create `middleware.ts`:

```ts
import { createServerClient } from "@supabase/ssr";
import { NextResponse, type NextRequest } from "next/server";

export async function middleware(request: NextRequest) {
  let response = NextResponse.next({ request });

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll();
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) => request.cookies.set(name, value));
          response = NextResponse.next({ request });
          cookiesToSet.forEach(({ name, value, options }) => response.cookies.set(name, value, options));
        },
      },
    }
  );

  const { data: { user } } = await supabase.auth.getUser();

  const { pathname } = request.nextUrl;
  const isDashboard = pathname.startsWith("/dashboard");
  const isAdmin = pathname.startsWith("/admin");

  if ((isDashboard || isAdmin) && !user) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (isAdmin && user) {
    const adminEmails = (process.env.PLATFORM_ADMIN_EMAILS ?? "")
      .split(",")
      .map((email) => email.trim().toLowerCase())
      .filter(Boolean);
    if (!adminEmails.includes((user.email ?? "").toLowerCase())) {
      return NextResponse.redirect(new URL("/dashboard", request.url));
    }
  }

  return response;
}

export const config = {
  matcher: ["/dashboard/:path*", "/admin/:path*"],
};
```

### Task 5: `create_restaurant_with_owner` RPC (`05_auth.sql`)

**Files:**
- Create: `supabase/sql/05_auth.sql`

**Interfaces:**
- Consumes: the `restaurants` and `staff_users` tables from `supabase/sql/01_schema.sql` (already live).
- Produces: a Postgres function `create_restaurant_with_owner(p_name text, p_slug text, p_type text, p_whatsapp_number text) returns uuid`, callable by `authenticated` users only. Task 6 (onboarding) calls this by name with these exact four parameter names.

- [ ] **Step 1: Create the file**

Create `supabase/sql/05_auth.sql`:

```sql
-- 05_auth.sql
-- Bootstrap RPC for new-owner signup. Paste into Supabase Studio's SQL
-- Editor and run AFTER 01_schema.sql, 02_rls.sql, 03_storage.sql, and
-- 04_seed.sql are already applied.
--
-- restaurants has no INSERT policy (02_rls.sql), and staff_users' write
-- policy requires is_staff_of(restaurant_id) to already be true — circular
-- for a brand-new restaurant's very first staff row. This function is the
-- one deliberate, narrow bypass: it creates both rows for the calling
-- (already-authenticated) user in one transaction.

create function create_restaurant_with_owner(
  p_name text,
  p_slug text,
  p_type text,
  p_whatsapp_number text
)
returns uuid
language plpgsql
security definer
set search_path = ''
as $$
declare
  new_restaurant_id uuid;
begin
  if auth.uid() is null then
    raise exception 'not authenticated';
  end if;

  insert into public.restaurants (name, slug, type, template_id, whatsapp_number, phone)
  values (p_name, p_slug, p_type, p_type, p_whatsapp_number, p_whatsapp_number)
  returning id into new_restaurant_id;

  insert into public.staff_users (restaurant_id, auth_user_id, name, phone, role)
  values (new_restaurant_id, auth.uid(), p_name, p_whatsapp_number, 'owner');

  return new_restaurant_id;
end;
$$;

revoke execute on function create_restaurant_with_owner(text, text, text, text) from public;
grant execute on function create_restaurant_with_owner(text, text, text, text) to authenticated;
```

- [ ] **Step 2: Manual consistency check**

Read the file back and confirm:
- `public.restaurants` and `public.staff_users` are the exact table names from `01_schema.sql`, and every column referenced (`name`, `slug`, `type`, `template_id`, `whatsapp_number`, `phone`, `restaurant_id`, `auth_user_id`, `role`) exists on those tables per `01_schema.sql`.
- `p_type` is passed for both `type` and `template_id` — intentional, matching every existing restaurant in `04_seed.sql` where `template_id` always equals `type`.

// seeded in supabase/sql/04_seed.sql, and links each to its staff_users row via
// auth_user_id. Run locally once, after filling SUPABASE_SERVICE_ROLE_KEY in

// Uses the service_role key (Supabase's Admin API) — never commit that key,
// never run this against a database with real customers.
//
// Email domain note: RFC 2606-reserved test domains (.example, .test, .invalid)
// are rejected outright by Supabase's own signup validation — confirmed live
// during this feature's implementation (a .example address failed with
// "Email address ... is invalid" before any auth row was created, while the
// identical flow with a real-MX domain succeeded). These addresses therefore
// use gmail.com with high-entropy, obviously-synthetic local parts — nobody
// owns these, but the domain itself resolves, so Supabase's validation passes.

import { createClient } from "@supabase/supabase-js";

const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
const serviceRoleKey = process.env.SUPABASE_SERVICE_ROLE_KEY;

if (!url || !serviceRoleKey) {
  console.error("Missing NEXT_PUBLIC_SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY in .env.local");
  process.exit(1);
}

const admin = createClient(url, serviceRoleKey, { auth: { autoRefreshToken: false, persistSession: false } });

const DEMO_PASSWORD = "TlabliDemo123!";

const staff = [
  { name: "Rami Abou Chacra", email: "rami.tlablidemo1@gmail.com" },
  { name: "Nadine Fares", email: "nadine.tlablidemo2@gmail.com" },
  { name: "Karim Haddad", email: "karim.tlablidemo3@gmail.com" },
  { name: "Sara Khalil", email: "sara.tlablidemo4@gmail.com" },
  { name: "Jean Nassar", email: "jean.tlablidemo5@gmail.com" },
  { name: "Elie Matta", email: "elie.tlablidemo6@gmail.com" },
  { name: "Tarek Younes", email: "tarek.tlablidemo7@gmail.com" },
];

for (const person of staff) {
  const { data: created, error: createError } = await admin.auth.admin.createUser({
    email: person.email,
    password: DEMO_PASSWORD,
    email_confirm: true,
  });
  if (createError) {
    console.error(`FAILED creating ${person.name} (${person.email}):`, createError.message);
    continue;

    .update({ auth_user_id: created.user.id })
    .eq("name", person.name);

  if (updateError) {

  } else {

}
